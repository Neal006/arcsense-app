# Findings: where the brief, the firmware spec and the data disagree

These were found by checking the documents in `docs/reference/` against the session 0007 data in `data/reference/session_0007/`. Each item records what the software does about it. Items marked **OPEN** need an answer from the firmware or trial team.

| ID | Finding | Evidence | What the software does | Status |
|---|---|---|---|---|
| F-01 | A Freeze Index (FI) threshold of 2.0 would raise alarms during healthy walking. | In `S_L_0007.CSV` the FI has mean 1.91 and max 4.11; 24 of 54 strides are at or above 2.0 and 8 of 54 at or above 3.0. The report claims "mean 0.41, peak 0.84", which disagrees with its own CSV. | The FoG rule is FI ≥ threshold (default **3.0**) for **N consecutive** strides (default 2), and both values are user settings. A regression test checks that the 0007 replay never raises a FoG alert with the defaults. | OPEN: the firmware team needs to explain the FI scaling. |
| F-02 | `asymmetryIndex` is a fraction, not a percentage. | CSV values run from 0.000 to 0.103. The report's "2.75%" equals 0.0275 × 100. | The UI multiplies by 100. A setting (default *fraction*) controls how the BLE float is read. The telemetry packet sends percent × 10, which is converted to a fraction. | OPEN: confirm the BLE float scale. |
| F-03 | The single-device asymmetry can't be the bilateral formula. | `|L−R|/mean` needs both ankles, but only L was recorded. | The app computes its own true L/R asymmetry from both streams. The ML features keep the firmware value so firmware and phone see the same inputs. | OPEN |
| F-04 | The brief's baseline ranges are wrong. | Brief: shock 1.0–1.8 g, length 1.2–1.7 m. Data: shock 2.2–5.8 g, length 0.0–1.22 m, stance 0.77–0.89 s. | Display ranges in `norms.ts` come from the data and the report's normative table. | Resolved |
| F-05 | The AI label is declared `int8` but uses 255 as a sentinel. | The CSV writes `-1`. | Decoded as `u8`. Both `0xFF` and `-1` map to "no inference". | Resolved |
| F-06 | Sync jitter under 2 ms between two BLE links isn't reachable from a phone. | Each write is delivered at that link's next connection event (7.5 ms or more on Android, 15 ms or more on iOS), and the two links aren't phase-locked. | Back-to-back write-without-response, with each dispatch time logged. Alignment uses the tokens recorded in both BIN files, and the residual skew is measured by `align_bilateral`. | Accepted limitation |
| F-07 | The meaning of `label_marker` in the BIN record is unclear. | The firmware spec calls it a "continuous per-sample sequence ID". The brief says label IDs are written into the SD stream. In session 0007 it is **0 for every valid sample**. | The **app marker log** (phone timestamps) is the authoritative ground truth. Labels are mapped onto the device timeline through the sync tokens. The BIN reader detects whether `label_marker` is zero, a sequence, or sparse labels, and reports which. | OPEN: what does the firmware write there? |
| F-08 | Two different BLE payload formats are documented. | The brief lists 8 separate float characteristics. The firmware spec lists one 20-byte `BleGaitTelemetryPacket` with no UUID. | The app decodes both. The GATT validation report shows which one the device exposes. The packet decoder stays disabled until a UUID is known. | OPEN: the packet's UUID. |
| F-09 | The existing BIN-to-CSV converter keeps a torn record. | The last row of `I_L_0007.csv` (sample 32177: gyro −1652/−959 dps, sync 9549, label 50197) straddles the 512-byte SD sector boundary at 643584. Everything after it is stale data from before, preallocated to 10 MB. | `bin_reader` ends the data at the last sector boundary before the first invalid record and reports torn records. It produces 32177 valid samples. | Report to firmware team |
| F-10 | BIN `sensor_time` isn't uniform and is only 24 bits wide. | Within each 18-sample FIFO batch the step is exactly 64 ticks (2.5 ms). Between batches it varies from 46 to 99 ticks. The mean is 65.1 ticks (393.2 Hz). The counter wraps every 655.36 s. | The reader unwraps the 24-bit counter and provides both the sample index and the device time in µs. The CSV's `timestamp_us = index × 2500` is nominal, not measured. | Resolved |
| F-11 | Cadence formula. | The brief's feature list uses `60/strideTime` (strides/min). The report's 91.95 spm equals `120/strideTime` (steps/min). | Steps per minute, `120/strideTime`, everywhere. | Resolved |
| F-12 | The offline validation swaps stance and swing. | `offline_strides.csv` gives stance 0.12 s and swing 1.26 s. `firmware_comparison.csv` shows a delta of about 0.7 s. | Not used as ground truth. | Report to analysis owner |
| F-13 | Nothing in the GATT map starts or stops an SD session. | — | Start writes `sessionStartTimestamp` (`0x000C`), then the first sync token. | OPEN: what does writing `0x000C` do? |
| F-14 | Session 0007 lost about 1.37 s of IMU records on the SD card, although the report claims "0 drops". | BMI270 `sensor_time` shows 16 gaps longer than 10 ms, totalling 1.37 s (the largest is 280 ms at t = 68.7 s), which explains the 393.2 Hz mean rate. The firmware's DSP index does **not** skip: DSP index n lines up with BIN device time n × 10 ms (MID_SWING gyro peaks agree to a median of 2.5 ms, IQR 0.7–4.7 ms), while BIN record count ÷ 4 drifts by more than 230 samples after the gaps. So the samples were processed by the DSP but never written to SD: these are real logging drops, not timestamp jumps. The converter's `timestamp_us = index × 2500` hides this. | `arcsense-qa` warns when the largest gap exceeds 50 ms. Strides and events are placed on the BIN timeline by device time (`sampleIndex × 10 ms`), never by record index. A regression test pins this on session 0007. | OPEN: firmware team to fix the SD logging stalls and to enable the sequence counter (F-07). |
